# Keynote maintenance

## Boundary

The public surface is `open`, `drop`, and `show`. `commands.py` validates the extension against [`file-authority.json`](file-authority.json) before shared AirDrop. Shared code owns regular-file/path/size validation, private allowlists, one-attempt snapshots and transfer, unlock handling, and result projection. The lab manifest is launch-only.

## File authority

Apple Keynote 15.3 documentation admits `.key`, `.ppt`, `.pptx`. This source authority permits validation and testing; it does not prove recipient receipt, import, rendering, or exact opening. Unsupported formats fail before AirDrop. The app gate cannot enlarge private transport configuration.

## Collaboration and mutation

Apple documents opening exact invitation links but does not publish a stable host/path/token grammar. Without a task-owned generated link, there is no route allowlist. Do not synthesize, decode, rewrite, or append opaque identifiers. Collaboration prompts, iCloud/Apple Account gates, edits, exports, printing, sharing, and deletion remain manual and outside production.

## Evidence

Exact-profile compatibility is bound to Keynote 15.3, `iPad17,1`, `J817AP`, and `23G83`. `open` needs inspected pixels for promotion. AirDrop requires manual recipient selection; `show` additionally needs proof that the intended file opened. No screenshot, path, filename, document content, collaboration token, or unique device identifier belongs in committed evidence.

## Manual PPTX evidence

A fresh minimal PPTX sent through `show` was selected manually in AirDrop. A subsequent read-only screenshot showed the exact filename and slide open in Keynote. The fixture's marker text was not visibly rendered, so this proves receipt/import/exact-file opening but not content fidelity. Standalone `drop` and other admitted formats remain unverified.
